# BTC 개인 자동매매 · 모의매매 MVP

업비트 `KRW-BTC` 공개 시세를 받아 이동평균 교차 전략을 실행하는 개인용 모의매매 시스템입니다.
모의매매·백테스트는 API 키가 필요하지 않습니다. **실거래는 별도 설정과 화면의 시작 조작이 필요하며 기본 비활성화입니다.**

## 실행

Python 3.9 이상, macOS 또는 Linux 환경에서 실행합니다.

**macOS:** 프로젝트 폴더의 `서버시작.command`를 더블클릭하면 서버가 백그라운드에서 시작되고
관리 화면이 열립니다. `서버중지.command`를 더블클릭하면 시세 수집까지 종료합니다.
터미널 창을 닫아도 서버는 계속 실행됩니다. 컴퓨터 재부팅 후 자동 시작은 하지 않습니다.

**터미널:** 프로젝트 폴더에서 다음 명령을 사용합니다.

```sh
./server start          # 백그라운드 시작
./server start --open   # 시작하고 관리 화면 열기
./server stop           # 정상 종료
./server restart        # 재시작 (자동매매는 정지 상태)
./server status         # 실행 상태 확인
./server logs           # 최근 서버 로그 확인
```

첫 시작에 `.venv`와 필수 패키지를 자동으로 준비합니다. 이미 실행 중이면 중복 실행하지 않습니다.
서버를 중지해도 가상 잔고와 거래 기록은 보존합니다. 실행 정보와 로그는 `.run/`에 저장합니다.
로그는 자동 순환하지 않으므로 장기 운영 시 서버를 중지한 뒤 `.run/server.log`를 정리할 수 있습니다.
이 실행기로 시작한 프로세스만 종료하며, 다른 프로그램이 8000 포트를 쓰면 충돌을 안내합니다.
기존에 직접 실행한 Uvicorn은 해당 터미널에서 `Ctrl+C`로 종료한 뒤 실행기를 사용하세요.

직접 실행하려면:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
uvicorn trade.app:create_app --factory --host 127.0.0.1 --port 8000 --workers 1
```

[관리 화면](http://127.0.0.1:8000)을 열고 시세 수신을 확인한 뒤 **거래 시작**을 누릅니다.
기본 가상 예산은 100만원입니다. 기본 전략은 확정된 1시간봉 MA 5/20 교차로, 신호가 없으면 거래하지 않습니다.
화면은 5초마다 갱신하고 시세는 30초마다 수집합니다.

- **거래 시작:** 새로운 전략 판단과 모의 체결을 처리합니다.
- **거래 정지:** 모든 전략 거래를 중지하고 시세 수집은 유지합니다. 보유 BTC를 매도하지 않습니다.
- **신규 매수 중지:** 매수만 차단하고 매도 신호는 계속 처리합니다.
- **신규 매수 재개:** 최신 시세와 일일 손실 한도 검사 후 매수 차단을 해제합니다.

서버 재시작 후에는 항상 거래 정지 상태입니다. 자금·체결·매수 중지 상태는 보존합니다.
시세 오류가 발생해도 거래를 정지하며, 수신 복구 후 시작 버튼으로 재개해야 합니다.

## 백테스트 · 성과 분석

관리 화면의 **백테스트 · 성과 분석** 탭에서 전략·기간·초기 자금·주문 금액·전략별 파라미터·비용·위험 한도를
입력한 뒤 **백테스트 실행**을 누릅니다. 한국시간 날짜 기준 어제까지, 최대 365일의 1시간봉을 검증합니다.
이 설정은 백테스트에만 적용되며 실시간 모의계좌 설정과 잔고는 변경하지 않습니다.

- 업비트 과거 OHLCV 캔들을 최대 200개씩 거슬러 수집하고 SQLite에 저장합니다. 완전히 저장된 구간은 API 재호출 없이 재사용합니다.
- 시작일 이전 `장기 이동평균 + 1`개 캔들을 준비 구간으로 수집합니다. 준비 구간은 거래·성과에 포함하지 않습니다.
- 확정된 캔들 시점의 전략을 판단하고 **다음 캔들 시가**에 수수료·슬리피지를 적용합니다. 현재 봉 종가를 보고 같은 봉 시가에 체결하지 않습니다.
- 페이지 경계가 잘못되거나 수집이 완료되지 않으면 계산을 중단합니다. 정상 수집에도 존재하는 누락 캔들은 보간하지 않고 개수를 표시합니다. 누락 전후에는 충분한 연속 캔들이 쌓일 때까지 신호를 보류합니다. 시세 수집과 백테스트는 별도 스레드에서 처리하고, 백테스트는 한 번에 하나만 실행합니다.
- 기존 모의매매의 주문 금액·BTC 비중·최소 주문 금액·일일 손실 한도를 재사용합니다. 일일 기준 자산은 한국시간 첫 시가 관측에서 설정합니다.
- 일일 손실 한도는 각 봉 시가에서 검사합니다. 도달 후 신규 매수 중지는 해당 백테스트 종료까지 유지합니다. 매도 신호는 계속 처리합니다.
- 종료 시 남아 있는 BTC는 강제 매도하지 않고 마지막 종가로 평가합니다. 따라서 미청산 자산에는 가정 매도 비용을 차감하지 않습니다.

성과 화면은 다음을 제공합니다.

| 지표 | 계산 기준 |
|---|---|
| 수익률 | `(최종 평가 자산 / 초기 자금 - 1) × 100` |
| 최대 낙폭(MDD) | 초기 자금부터 시가·체결 직후·종가 평가액의 최고점 대비 최대 하락률 |
| 승률 | 배분 원가·수수료 반영 후 이익이 난 매도 체결 / 전체 매도 체결. 일부 매도도 1회로 계산하며 매도가 없으면 미정 |
| 실현·평가 손익 | 매도 완료 이익과 남은 BTC의 종가 평가 손익을 구분 |
| 단순 보유 비교 | 초기 자금 전액을 첫 시가에 매수하고 같은 수수료·슬리피지 적용 후 마지막 종가로 평가 |
| 초과 수익률 | 전략 수익률 − 단순 보유 수익률 (`%p`) |

단순 보유는 BTC에 전액 투자하므로 전략의 기본 보유 상한 30%와 위험 노출이 다릅니다.
봉 내부의 가격 경로·호가·부분 체결은 재현하지 않습니다. 그래프는 봉 종가별 자산·낙폭을 표시하며,
요약 MDD에는 시가와 체결 직후 관측값도 포함하므로 그래프의 최대 낙폭과 차이가 날 수 있습니다.
과거 성과는 미래 수익을 보장하지 않습니다.

결과와 캔들은 모의계좌 DB 옆의 `<계좌 DB 이름>-backtests.sqlite3`에 저장합니다.
기본 파일은 `data/trade-backtests.sqlite3`입니다. 최근 30개 결과를 화면에서 선택할 수 있고
전체 체결은 UTF-8 BOM CSV로 다운로드할 수 있습니다. 화면의 체결 목록은 최근 100건입니다.
수집 실패 시 부분 캐시는 남고 결과는 저장하지 않습니다. 정상 완료한 결과만 기록합니다.

API: `POST /api/backtests`, `GET /api/backtests`, `GET /api/backtests/{id}`,
`GET /api/backtests/{id}/trades.csv`. 백테스트 실행 요청은 수집·계산 완료 후 응답합니다.

### 세 전략 비교

**세 전략 비교**를 누르면 동일한 캔들·기간·초기 자금·주문 한도·비용·위험 한도로
이동평균 교차, 정액 분할매수, 목표 비중 리밸런싱을 각각 실행합니다.
각 실행은 독립된 가상 계좌에서 시작하고 결과를 각각 저장합니다. 비교 표의 **상세 보기**로 그래프와 거래 내역을 전환합니다.
API는 `POST /api/backtests/compare`이며 단일 백테스트와 같은 요청 필드를 사용합니다.
목표 비중이 최대 BTC 비중보다 높으면 비교 실행을 거부합니다.

## 지원 전략

한 번에 하나의 전략을 실행합니다. 전략 설정 화면에서 거래 정지 후 선택·저장할 수 있습니다.

| 전략 | 매수 | 매도 | 전용 설정 |
|---|---|---|---|
| 이동평균 교차 (`ma_cross`) | 단기 MA 상향 교차 | 하향 교차 시 보유 BTC 전량 | 단기·장기 기간 |
| 정액 분할매수 (`dca`) | 고정 주기마다 주문 금액만큼 | 자동 매도 없음 | 1·4·6·12·24·48·168시간 주기 |
| 목표 비중 리밸런싱 (`rebalance`) | BTC 비중이 목표−편차 미만 | 목표+편차 또는 최대 비중을 초과하면 일부 매도 | 목표 BTC 비중·허용 편차 |

분할매수 시각은 UTC 1970-01-01 00시(한국시간 09시) 기준 주기 경계입니다.
기본 24시간은 매일 한국시간 09시, 168시간은 매주 목요일 09시입니다.
캔들 확정 후 2분 이내에만 판단하며 서버가 중단됐거나 거래를 정지한 동안 놓친 회차는 소급 매수하지 않습니다.
외부 원화 입금이나 가상 현금 추가 없이 기존 운영 예산 안에서만 매수하며 보유 한도·매수 중지 규칙을 따릅니다.

리밸런싱의 기본 목표는 BTC 20%, 허용 편차는 ±2%p입니다. 예를 들어 18% 미만이면 매수,
22%를 초과하면 매도하고 경계값에서는 대기합니다. 목표 비중은 최대 BTC 비중 이하여야 하며
허용 편차는 목표보다 작아야 합니다. 주문 한도·최소 금액·수수료·슬리피지를 적용하므로 목표에 즉시 도달하지 않을 수 있습니다.
매수와 매도 모두 1회 주문 금액으로 제한합니다. 일부 매도 시 평균 매입 원가를 매도 수량에 비례해 배분하고
남은 BTC 원가를 유지합니다. 매수 중지 상태에서도 리밸런싱 매도는 허용합니다.
전략 변경 자체는 주문을 만들지 않으며, 이미 판단한 캔들을 다시 처리하지 않습니다.

## 기본 운영 규칙

| 항목 | 기본값 |
|---|---|
| 가상 초기 원화 | 1,000,000원 |
| 1회 매수 금액 | 최대 100,000원 + 수수료 |
| 최대 BTC 보유 비중 | 평가 자산의 30% |
| 일일 손실 한도 | 기준 자산 대비 3% 하락 시 신규 매수 차단 |
| 가정 편도 수수료 | 0.05% |
| 가정 편도 슬리피지 | 0.1% |
| 최소 모의 주문 금액 | 5,000원 |

수수료·슬리피지·최소 금액은 시뮬레이터의 가정입니다. 실제 계정 조건을 조회한 값이 아닙니다.
매수 금액은 현금·보유 비중 한도에 따라 줄어들 수 있습니다. 이동평균의 매도 신호는 BTC 전량,
리밸런싱은 목표 비중에 필요한 일부 수량을 매도하며 분할매수는 자동 매도하지 않습니다.
원화는 Decimal, BTC 수량은 8자리 내림으로 계산합니다. 수수료는 매수 원가에 포함하고 매도 수익에서 차감합니다.

캔들 확정 후 2분 이내의 교차만 사용합니다. 진행 중인 캔들, 누락 구간, 과거 신호의 재실행은 배제합니다.
모의 체결가는 판단 시점 이후 수신한 현재가에 슬리피지를 적용합니다. 확정 캔들 종가에 소급 체결하지 않습니다.
같은 캔들의 판단·체결·잔고 변경은 SQLite 트랜잭션 하나로 기록해 재시작과 중복 수신에 대응합니다.

일일 손실 기준은 한국시간 날짜별 **첫 정상 시세 관측 시점의 평가 자산**입니다.
자정에 수집이 중단되어 있었다면 정확한 자정 자산과 다를 수 있습니다.
매수 차단은 날짜가 바뀌어도 유지하며, 수동으로 재개합니다. 자동 손절·자동 청산 기능은 없습니다.

## 전략 설정 화면

관리 화면의 **전략 설정** 탭에서 실행 전략, 단기·장기 이동평균, 분할매수 주기,
리밸런싱 목표·편차, 1회 주문 금액, 최대 BTC 비중, 일일 손실 한도를 변경할 수 있습니다.

1. 실시간 모의매매 화면에서 **거래 정지**를 누릅니다. 신규 매수 중지만으로는 수정할 수 없습니다.
2. 전략 설정 탭에서 값을 수정하고 **설정 저장**을 누릅니다.
3. 실시간 화면에서 운영 규칙을 확인한 뒤 **거래 시작**을 누릅니다.

입력 조건은 `1 ≤ 단기 < 장기 ≤ 199`, 주문 금액은 5,000원 이상·초기 예산 이하,
BTC 비중은 0% 초과·100% 이하, 일일 손실 한도는 0% 초과·100% 미만입니다.
장기 199봉의 판단에 필요한 확정 캔들 200개를 수집합니다.
입력 중에는 화면 자동 갱신이 수정 내용을 덮어쓰지 않으며 **수정 취소**로 현재 저장값을 다시 불러옵니다.

설정은 계좌 DB에 저장하고 재시작 시 복원합니다. 저장·재시작 후 거래는 정지 상태입니다.
잔고·체결·일일 기준 자산은 유지하며, 새 한도를 낮춰도 기존 BTC를 자동 매도하지 않습니다.
이미 판단한 캔들을 새 설정으로 재실행하지 않고 이후의 새로운 캔들에서 판단합니다.
신규 매수 중지는 설정 저장으로 해제되지 않습니다. 낮춘 손실 한도는 다음 시세 수신 때 검사합니다.
변경 전·후 값은 운영 기록에 남습니다. 초기 자금·캔들 단위·수수료·슬리피지는 화면 변경 대상이 아닙니다.
백테스트의 설정과 결과는 별도로 유지됩니다. API는 `POST /api/settings`이며 기존 5개 필드를 함께 전송하고
전략·매수 주기·목표·편차는 추가 필드로 지정합니다. 기존 계좌는 잔고를 보존한 채 이동평균 전략을 기본으로 호환합니다.

## 설정

### 업비트 실거래

관리 화면의 **실거래** 탭에서 별도 실거래 예산·봇 보유 BTC·손익·주문 상태를 확인합니다.
모의매매·백테스트 기록은 실거래에 사용하지 않습니다.

1. 업비트에서 주문조회·주문하기 권한의 API 키를 발급하고 서버의 외부 공인 IP를 허용 목록에 등록합니다.
   출금 기능은 구현하지 않았으며 출금 권한은 부여하지 않습니다.
2. 환경변수로 키와 운영 예산을 설정한 터미널에서 서버를 재시작합니다.
3. 실거래 탭에서 **계좌 연결 확인** 후 실거래 전략·한도를 검토하고 저장합니다.
4. **주문 테스트 (미체결)**로 업비트의 주문 요청 검증 API를 호출합니다. 실제 주문은 생성하지 않습니다.
5. 실제 주문 동의 체크 후 **실거래 시작**을 누릅니다. 시작에는 최근 5분 이내 테스트와 최신 계좌·시세가 필요합니다.

```sh
export UPBIT_ACCESS_KEY='본인 Access Key'
export UPBIT_SECRET_KEY='본인 Secret Key'
export TRADE_LIVE_BUDGET_KRW=100000
export TRADE_LIVE_ORDER_CAP_KRW=10000
# 먼저 false 상태에서 계좌 연결과 미체결 주문 테스트를 확인할 수 있습니다.
export TRADE_LIVE_ENABLED=false
./server restart
# 실제 주문을 사용할 때 true로 바꾸고 재시작한 뒤 화면에서 다시 테스트·시작합니다.
```

`.env`는 자동 로드하지 않습니다. 키는 브라우저·DB·로그·응답에 저장하지 않습니다.
키가 설정되면 서버는 거래 정지 상태에서도 계좌·호가·미해결 주문을 주기적으로 조회합니다.
`TRADE_LIVE_ENABLED=false`에서는 실제 주문 생성 경로 자체를 차단합니다.
기존 주문 조회·취소와 미체결 주문 테스트는 이 스위치가 false여도 가능합니다.

실거래 정책:

- 기본 운영 예산 10만원, 1회 매수 상한 1만원입니다. 실제 사용 가능 원화가 운영 장부 잔액보다 적으면 새 주문을 중지합니다.
  화면의 운영 장부는 할당 예산·봇 체결 기준이며 업비트 계좌 전체 잔고와 다릅니다. 예산은 거래소에서 따로 잠그거나 이체하지 않습니다.
- 처음에는 봇 BTC를 0으로 시작합니다. 기존 BTC를 자동으로 가져오거나 매도하지 않습니다. 봇이 확인한 매수 체결 수량만 매도 대상으로 관리합니다.
- 실거래 설정은 최초 모의매매 전략을 복사한 뒤 독립적으로 저장합니다. 초기 실거래 주문 금액은 매수 상한으로 줄입니다.
  이후 모의매매 설정 변경은 실거래 설정을 바꾸지 않습니다. 설정 변경 후에는 주문 테스트를 다시 해야 합니다.
- 주문은 **지정가 IOC + SMP cancel_taker**입니다. 공개 현재가 대비 `TRADE_SLIPPAGE` 범위 안에서 매수 상한·매도 하한을 정하고
  거래소 호가 단위로 보수적으로 반올림합니다. 미체결 잔량은 취소되며 미체결·부분 체결을 자동으로 재주문하지 않습니다.
- 주문 가능 정보에서 실제 bid/ask 수수료, 최소 금액, 지원 유형·호가를 확인합니다. 장부에는 가정 비용이 아닌 실제 체결 금액·수수료를 반영합니다.
- 1회 **매수** 상한입니다. 이동평균 매도는 봇 BTC 전량을 대상으로 하며 리밸런싱 매도는 설정한 주문 금액으로 제한합니다.
- 부분 체결은 누적 수량·금액·수수료의 증가분만 적용합니다. 일부 매도 원가는 평균 원가에서 수량 비례로 배분합니다.
  장부·체결 내역·주문 누적값을 같은 트랜잭션으로 저장합니다.
- 주문 의도와 고유 identifier를 전송 전에 저장합니다. 응답이 끊기면 같은 identifier로 **조회만** 하며 주문 생성 요청을 재전송하지 않습니다.
  미확인 주문이 있는 동안 새 주문과 설정 변경을 막습니다. 계속 미확인이라면 업비트 주문 내역과 운영 기록을 대조해야 하며 자동 해제 기능은 없습니다.
- 취소 접수 응답만으로 취소 완료로 간주하지 않습니다. 조회 응답으로 최종 상태와 취소 중 체결된 수량을 확인합니다.
- **실거래 정지**는 새 주문을 막고 미전송 의도를 폐기합니다. 이미 접수된 주문은 체결될 수 있으므로 개별 취소와 최종 상태 확인이 필요합니다.
- 서버 재시작 후 실거래는 항상 정지 상태입니다. 미전송 주문 의도는 폐기하고, 전송 여부가 불명확하거나 접수된 주문은 조회·동기화합니다.
  서버를 종료해도 거래소에 접수된 주문 자체를 되돌리거나 취소하지 않습니다.
- 예산·주문·잔고·일일 손실 기준은 실거래 장부에서 계산합니다. 손실 한도는 신규 매수만 차단하며 강제 청산하지 않습니다.
- 같은 업비트 계좌에서 수동 주문·다른 봇·출금을 병행하면 가용 잔고가 달라질 수 있습니다. 부족분은 자동 보충하거나 초기화하지 않고 거래를 정지합니다.
- 기본 기록은 `data/trade-live.sqlite3`입니다. 실행 중인 실거래 장부는 파일 잠금으로 중복 실행을 막습니다.
  API 키의 해시로 기록을 연결하므로 다른 키로 바꾸면 조회·거래를 막습니다. 키 교체·만료 시 기존 장부·미해결 주문을 확인한 뒤 별도 이관이 필요합니다.
  **장부 삭제로 차단을 해제하면 봇 보유 수량과 미해결 주문을 잃습니다.**

키가 없는 개발 환경에서는 가짜 거래소로 인증·부분 체결·취소·응답 유실·재시작·장부 분리를 테스트했습니다.
실제 계정의 인증·주문 테스트·실거래 체결은 검증하지 않았습니다.

API: `GET /api/live/status`, `POST /api/live/connect`, `POST /api/live/test`,
`POST /api/live/start` (`acknowledge_real_orders: true` 필수), `POST /api/live/control/{action}`,
`POST /api/live/settings`, `POST /api/live/orders/{identifier}/cancel`.

공식 문서: [인증](https://docs.upbit.com/kr/reference/auth),

### 텔레그램 알림

전략 설정 탭의 **텔레그램 알림**에서 설정 상태, 전송 대기·완료·실패 건수,
최근 10개 내역을 확인하고 **테스트 알림 보내기**를 누를 수 있습니다.
실제 수신을 확인하기 전에는 봇 연결이 검증된 것으로 간주하지 않습니다.

1. 텔레그램의 공식 [BotFather](https://t.me/BotFather)에서 봇을 만들고 봇 토큰을 발급합니다.
2. 알림을 받을 본인 채팅에서 생성한 봇에 `/start`를 보냅니다.
3. 공식 [getUpdates](https://core.telegram.org/bots/api#getupdates)의 `message.chat.id`로 수신 채팅 ID를 확인합니다.
4. 아래 두 환경변수를 설정한 터미널에서 서버를 재시작합니다.

```sh
export TRADE_TELEGRAM_BOT_TOKEN='본인 봇 토큰'
export TRADE_TELEGRAM_CHAT_ID='본인 채팅 ID'
./server restart
```

`.env.example`의 두 항목에도 설정 예시가 있습니다. `.env`는 자동으로 읽지 않으므로
환경변수를 설정한 터미널에서 실행해야 합니다. 더블클릭 실행기는 해당 터미널의 환경변수를 자동 상속하지 않습니다.
키를 코드·Git·브라우저 입력란에 저장하지 않으며, 알림 API는 토큰과 채팅 ID 값을 반환하지 않습니다.

- 대상: 모의 매수·매도 체결, 일일 손실 한도 도달, 시세 수집 장애, 시세 수신 복구.
- 시각은 한국시간으로 표시하며, 실제 주문이 아닌 모의매매임을 메시지에 명시합니다.
- 같은 장애가 계속되는 동안 반복 통지는 억제하고, 정상 수신 후 다시 발생한 장애는 새로 알립니다.
- 체결·위험 이벤트와 알림 대기열을 같은 DB 트랜잭션에 저장합니다. 전송은 별도 작업으로 처리합니다.
- 네트워크 오류는 30초부터 지수 간격으로 최대 5회 시도하며, 429 응답의 재시도 시간을 반영합니다.
  인증·수신 권한 등의 영구 오류는 즉시 실패 처리합니다. 테스트 알림 요청은 10초 간격입니다.
- 전송되지 않은 알림은 재시작 후 이어서 처리합니다. 봇 토큰이나 수신 채팅이 바뀌면 이전 설정의 대기 알림을 새 수신자에게 보내지 않습니다.
- Telegram 수락 직후 연결이 끊기거나 서버가 종료되면 재시도 때문에 중복 수신될 수 있습니다. 메시지의 알림 번호로 식별할 수 있습니다.
- 두 설정이 모두 없으면 알림은 비활성화되며 과거 이벤트를 소급 수집하지 않습니다. 백테스트는 알림을 보내지 않습니다.
- 이 기능은 실행 중인 서버가 감지한 시세 장애를 알립니다. 컴퓨터 종료·서버 프로세스 강제 종료 자체를 감시하는 외부 모니터는 포함하지 않습니다.

API: `GET /api/notifications`, `POST /api/notifications/test`.
전송은 공식 [sendMessage](https://core.telegram.org/bots/api#sendmessage)를 사용합니다.

### 실행 환경

`.env.example`에 지원하는 환경변수가 있습니다. `.env` 자동 로드는 하지 않습니다.

```sh
export TRADE_INITIAL_CASH=2000000
export TRADE_ORDER_KRW=100000
export TRADE_DB_PATH=data/scenario-2.sqlite3
./server start
```

화면에서 저장한 전략·위험 설정은 이후 실행 시 같은 항목의 환경변수보다 우선합니다.
초기 예산·캔들 단위·비용 등 화면에서 변경하지 않는 계좌 설정을 바꾸면 시작을 거부합니다.
다른 초기 예산이나 비용을 시험하려면 새 DB 경로를 지정하세요.
`data/trade.sqlite3`에 모든 상태를 보관합니다. 백업 시에는 서버를 종료한 후 DB를 복사하세요.
같은 DB의 동시 실행은 파일 잠금으로 방지합니다. Uvicorn은 단일 워커로 실행해야 합니다.
기본 주소는 로컬 전용이며, 인증 없는 관리 화면을 외부에 노출하지 마세요.

Docker가 있으면 `docker compose up --build -d`로 실행할 수 있습니다.
호스트의 `127.0.0.1:8000`에 연결하며 데이터는 `trade-data` 볼륨에 보관합니다.
Docker 구성은 제공되지만 현재 개발 환경에 Docker가 없어 실행 검증하지 않았습니다.

## 검증

```sh
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
```

전략 교차, 미래 캔들 제외, 누락 캔들, 수수료·슬리피지 손익, 보유 비중,
중복 신호, 재시작, 트랜잭션 롤백, 한국시간 날짜 전환, 손실 한도,
API 제어와 동일 DB 중복 실행 방지를 검증합니다. 테스트는 네트워크와 실제 주문을 사용하지 않습니다.

## 구조와 다음 단계

```text
trade/config.py      환경변수 및 설정 검증
trade/market.py      업비트 공개 REST 시세 수집
trade/strategy.py    확정 캔들 이동평균 교차 판단
trade/engine.py      거래 상태·위험 관리·가상 체결
trade/storage.py     SQLite 저장소
trade/backtest.py    과거 OHLCV 수집·캐시·백테스트·성과 분석
trade/notifications.py 텔레그램 전송·재시도
trade/exchange.py    업비트 인증·제한된 거래 API
trade/live.py        실거래 주문 의도·실제 체결·장부 동기화
trade/app.py         수집 루프·로컬 관리 API
trade/static/        한국어 대시보드
server              로컬 서버 시작·중지 명령
scripts/server.py   백그라운드 프로세스 관리
tests/              회계·위험·재시작·API 검증
```

이 버전은 실시간 모의매매, 웹 기반 백테스트, 텔레그램 알림 및 기본 실거래 연동을 지원합니다.
별도 백테스트 CLI와 입출금 기능은 구현하지 않았습니다.
초기 시세 로딩은 최대 200개 캔들이며 이후 관측한 캔들을 누적합니다.
가상 즉시 전량 체결을 가정하므로 실제 호가·대기열·부분 체결을 재현하지 않습니다.
전략 수익성을 검증한 결과는 아닙니다.
